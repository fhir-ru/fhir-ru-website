# Правила работы в fhir-ru-website

## Назначение и точки входа

Это репозиторий нового сайта FHIR.ru. Сначала читать `README.md`,
`spec/README.md` и документы инициативы, которой принадлежит задача.
Основная инициатива: `spec/initiatives/website_v1/`.

## Рабочий процесс

- Перед изменением определить инициативу и ID задачи backlog.
- Архитектуру и требования вести в `spec/architecture/`; решения — в
  `spec/decisions/`; процедуры — в `spec/procedures/`.
- Состояние работы вести в `status.md`, задачи и критерии — в `backlog.md`,
  результат рабочего инкремента — в `log/` соответствующей инициативы.
- Обновлять решения и спецификацию вместе с реализацией. Черновик,
  предложение, реализованное поведение и принятое решение различать явно.
- Не считать предположения о хостинге, дизайне и публикации IG утверждёнными
  только потому, что они описаны в первой спецификации.
- По завершении проверять изменения по критериям задачи и делать небольшой
  тематический коммит. Статус Done требует результата и записанной проверки.
- Новые инициативы оформлять по шаблонам `spec/initiatives/templates/`.

## Границы изменений

- RuCore, ГОСТ и RuAmb разрабатываются в собственных репозиториях. Здесь
  не создавать вторую редактируемую копию их исходников.
- Kostasoft использовать как ориентир для оболочки, компонентов и сборки.
  Не копировать зависимости, runtime, формы заявок и внутренние настройки.
- Перед любым копированием или созданием worktree оценить размер источника;
  переносить только нужные код, документацию и разрешённые материалы.
- Не хранить credentials, auth-файлы, локальные конфигурации доступа,
  зависимости, сборки IG и runtime state в Git.
- Локальные изменения и push исходников не разрешают deploy, remote jobs,
  изменение DNS, действующих серверов, доменов и архивирование других репозиториев.
  Для этих действий требуется явное указание пользователя в текущей задаче.
- Не добавлять автоматическую публикацию сайта без отдельного поручения.
- Не выбирать публичную лицензию за правообладателей; до решения не
  добавлять LICENSE и не объявлять весь сайт CC0 по лицензии базового FHIR.

## Проверка и содержание

- Для документации проверять внутренние ссылки, согласованность статусов,
  границы утверждённых решений и отсутствие секретов.
- Перед сдачей UI пройти изменённый путь во встроенном браузере Codex:
  ручной ввод, смена значений, основное действие, ошибка и исправление там,
  где они применимы. После правок перезагрузить страницу, проверить DOM,
  сообщения и консоль. Следовать действующим инструкциям по встроенному браузеру.
- Для IG проверять HTML, JSON/XML, canonical resolution, package.tgz,
  ссылки на версии и сохранность старых адресов; один HTTP 200 недостаточен.
- Проверять технические решения по первоисточникам конкретной версии FHIR.
- Публичные страницы содержат полезный контент сообщества. Служебную
  историю, результаты проверок и рабочие решения держать в `spec/`.
